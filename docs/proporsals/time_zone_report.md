# タイムゾーン対応 現状確認レポート

## 1. 現在のシステムのタイムゾーンの扱い

### 結論
現状は**部分的に UTC 前提の実装がある一方で、システム全体としての明示的なタイムゾーン仕様は未整備**です。特に「日付（date）系のAPI/ロジック」はクライアント・サーバー双方のローカル時刻に依存しうるため、利用者タイムゾーンが異なると日付ずれが起きる余地があります。

### 確認結果（バックエンド）
- DB の `DateTime` カラムは `datetime.utcnow` をデフォルトに使っており、UTC で記録する意図はあります（ただし timezone-aware ではなく naive datetime）。
- API の主要パラメータは `date`（`target_date`, `start_date`, `end_date`）であり、タイムゾーン情報を受け取るフィールドはありません。
- `date.today()` を用いた処理（ダッシュボード既定日や週計算など）があり、実行環境のローカルタイムゾーンに依存します。

### 確認結果（フロントエンド）
- 複数箇所で `new Date(...).toISOString().split('T')[0]` により日付文字列を生成しており、UTC 変換を経由するため、ローカル日付とのズレが起こり得ます。
- 一部（月次カレンダーのセル）では `getTimezoneOffset` で補正していますが、他箇所（初期選択日・前後日移動・週次クエリ範囲など）は同等補正が統一されていません。

## 2. （現状仕様が不足しているため）タイムゾーンを扱うための仕様の概要

### 2.1 基本方針
- **保存（DB）**: すべて UTC で保存する。
- **API 契約**: 日時を扱う項目は timezone-aware な ISO 8601 を許可/推奨し、日付 API は「どのタイムゾーンでの日付か」を明確化する。
- **表示（UI）**: ユーザー設定タイムゾーン（例: `Asia/Tokyo`）を基準に日付境界を扱う。

### 2.2 API 仕様案
- 選択肢A（推奨）: 既存の `date` API は維持しつつ、`X-Timezone` ヘッダ（IANA TZ）を追加。
  - 例: `X-Timezone: Asia/Tokyo`
  - サーバーはこの TZ に基づいて「今日」「週開始日」「日付範囲解釈」を行う。
- 選択肢B: `tz` クエリパラメータを全日付系エンドポイントに追加。
- バリデーション: 未指定時は既定値（例: `UTC`）にフォールバックし、レスポンスに適用TZを明示。

### 2.3 データモデル仕様案
- `DateTime` カラムは timezone-aware (`timezone=True`) を利用し、保存時は UTC に正規化。
- 日付（`Date`）は「ユーザーTZでのカレンダー日付」として扱うことを仕様化。
- 将来的にユーザープロファイルへ `timezone`（IANA 文字列）を追加。

### 2.4 フロントエンド仕様案
- 日付計算を `toISOString().split('T')[0]` ベースで統一しない。
- `Intl.DateTimeFormat`（または dayjs/luxon）で「ユーザーTZの YYYY-MM-DD」を生成するユーティリティを導入し、全画面で共通利用。
- 月/週/日移動と API リクエスト境界は同一ユーティリティを使って一貫化。

### 2.5 受け入れ基準（例）
- 異なるTZ（UTC/JST/PST）で同一ユーザーが同一日付を見たとき、仕様どおりの基準日で同じタスク集合が返る。
- 日付跨ぎ時刻（00:00 前後）で、前日/当日判定が想定どおり。
- DST 変更日でも週次・日次境界が崩れない。

## 3. 変更スコープ

### 3.1 バックエンド
1. タイムゾーン解決レイヤー追加
   - リクエストから `X-Timezone`（または `tz`）を取得し、検証してコンテキスト化。
2. `date.today()` 依存ロジック置換
   - ユーザーTZ基準の「today」算出へ変更。
3. DateTime の明確化
   - モデルを `timezone=True` に移行（段階導入可）。
4. テスト
   - TZ別・DST境界の API/サービス層テストを追加。

### 3.2 フロントエンド
1. 日付ユーティリティ新設
   - `formatDateInTZ(date, tz) => YYYY-MM-DD` など。
2. 既存画面の置換
   - カレンダー、Execution画面の `toISOString().split('T')[0]` 依存箇所を統一置換。
3. API 連携
   - `X-Timezone` 送信を axios 共通設定へ追加。
4. テスト
   - 日付変換ユニットテスト、E2Eで日付境界を確認。

### 3.3 マイグレーション/運用
- 既存 `DateTime` は UTC naive とみなし、移行時に UTC aware として再解釈。
- ロールアウトは「ヘッダ導入（互換あり）→ サーバー解釈変更 → UI統一」の順が安全。

---

## 4. 補足（判断）
- 「UTCで保存しているためタイムゾーン対応済み」とは言い切れません。
- 実運用上は**日付境界の扱い**（今日・週開始・API日付引数の生成）が最重要で、現状コードではその統一仕様が不足しています。
